## Database reviewer

Initial database reviewer verdict was BLOCKING. Findings and remediation:

- Expired owners could complete/fail before reclaim. Fixed by requiring PostgreSQL-clock-active leases on `complete`, `mark_retryable_failure`, and `mark_terminal_failure`; covered by `test_expired_owner_cannot_complete_or_fail_before_reclaim` and `test_db_clock_not_caller_clock_determines_expiration`.
- Bot configuration accepted invalid non-null bot IDs. Fixed with positive-ID repository validation and migration constraints for project/platform bot configuration; covered by bot-ID rejection tests and migration contract test.
- Platform bot ID persistence was absent from the application port. Fixed by adding get/set methods to `TelegramInboxRepositoryPort`.
- Process-restart recovery could not discover expired processing rows without knowing inbox IDs. Fixed by adding `reclaim_expired_batch(limit)` to the repository port/implementation; covered by concurrent batch reclaim and pool reconstruction recovery tests.
- Replacing project client/manager bot tokens could leave the old numeric bot account ID attached. Fixed by atomically clearing the corresponding numeric bot ID whenever the token is replaced or cleared; covered by token replacement/clearing coherence tests. Platform token replacement remains a future platform-onboarding contract because platform token persistence is outside S1.1.
- `TelegramUpdateIdentity` direct construction could bypass factory validation. Fixed with `__post_init__` invariant validation and strict bool rejection; covered by table-driven domain tests.
- Lease repository methods no longer accept caller `now`; DB-clock authority is explicit in the repository SQL and tests use PostgreSQL-relative successful lease deadlines.
- `ck_telegram_inbox_processing_owner` is now bidirectional: `processing` requires ownership fields and non-processing states require ownership fields to be `NULL`.
