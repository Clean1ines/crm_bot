# S1.1 — Durable Telegram Inbox Schema and Repository


## Goal

Create the authoritative PostgreSQL persistence boundary for Telegram update identity, durable acceptance, lifecycle, ownership, attempts, recovery metadata, and duplicate diagnostics.

## Current behavior

Client dedupe is Redis TTL based and manager/platform paths do not share one durable inbox. There is no authoritative PostgreSQL Telegram update lifecycle.

## Required behavior

- Persist one durable logical update identity.
- Identity includes surface/role, project or platform scope, stable non-secret Telegram bot account identity (preferred numeric bot ID from `getMe`, or approved generation identity), and Telegram `update_id`.
- Raw token, token hash, and webhook secret are forbidden in identity.
- Initial intake uses atomic insert semantics. A uniqueness conflict never resets lifecycle.
- Duplicate delivery may update isolated diagnostics such as duplicate count/time but must not overwrite status, owner, lease, attempts, completion, failure, payload, or outbound state.
- Same identity with different payload is an operator-visible anomaly and does not replace the original payload.
- Lifecycle supports states equivalent to received, processing, completed, retryable failed, and terminal failed.
- Attempts count actual processing attempts, not duplicate webhook deliveries.
- Claim/renew/reclaim primitives are repository-level atomic operations.

## In scope

- schema/migration;
- persistence model and repository port/implementation;
- stable identity value object/DTO where architecturally appropriate;
- lifecycle transition validation;
- owner token, lease expiry, attempt/error metadata;
- duplicate/anomaly diagnostics;
- migration and repository tests.

## Out of scope

- webhook handler refactor;
- worker loop;
- conversation thread lease;
- runtime state CAS;
- Telegram outbound sending;
- R17 tenant authorization;
- ticket close idempotency.

## Architecture constraints

- PostgreSQL is authority.
- Do not reuse knowledge/RAG domain lifecycle or vocabulary.
- Neutral repository/lease patterns may be adapted without importing unrelated capacity semantics.
- Existing data and migration rerun behavior must be explicitly handled.

## Task acceptance criteria

- S1.1-AC-01: concurrent inserts for one identity produce one row.
- S1.1-AC-02: replacing a project bot account allows a reused `update_id` to create a new identity; retry from the same new bot deduplicates.
- S1.1-AC-03: duplicate of completed work does not return it to received/processing.
- S1.1-AC-04: duplicate during processing does not alter owner or lease.
- S1.1-AC-05: duplicate after failure does not reset attempts or error metadata.
- S1.1-AC-06: same identity/different payload records anomaly and preserves original payload.
- S1.1-AC-07: one active owner can claim; stale owners cannot renew or complete.
- S1.1-AC-08: attempt count increments only on a real new claim/attempt.

## Required QA design

Include bot replacement, identity collision, every lifecycle state, concurrent insert/claim, stale owner, lease expiry, payload anomaly, migration rerun, existing-row compatibility, and bounded error metadata.

## Expected test levels

- migration tests;
- PostgreSQL repository integration tests;
- property/table-driven lifecycle transition tests;
- concurrency tests using separate transactions/connections.

## Impact and compatibility expectations

Recon must locate existing Telegram update dedupe keys, webhook handlers, manager/platform update entrypoints, repository conventions, migration runner semantics, and any generic work-item primitives considered for reuse.

## Migration/data requirements

Migration must be safe on clean and existing databases, have deterministic uniqueness, avoid secrets, and define rollback/forward-fix behavior.

## Observability requirements

Persist or emit bounded counters for duplicates, payload anomalies, stale claims, and exhausted attempts without logging secret material or full sensitive payloads unnecessarily.

## Validation gates

Focused repository/migration tests, affected DB tests, formatting/lint/type checks, full required backend quality gate, QA acceptance review.

## Rollback/degraded behavior

Schema may remain unused before S1.2. Do not route production webhook traffic through an incomplete lifecycle.

Update actual schema/persistence sections, R20 remediation progress, traceability planned-to-actual fields, and task evidence only after verification.
