# S1.7 — Integrated S1 Acceptance and Evidence


## Goal

Prove the complete S1 production-safety contract in integrated test and staging-like evidence without absorbing S2-S7 scope.

## Required behavior

- Execute all S1 release acceptance scenarios.
- Prove duplicate/restart/Redis-outage/PostgreSQL-outage/lease/CAS/outbound ambiguity behavior across real composition.
- Prove supported, unsupported, and handoff intake paths remain durable.
- Produce evidence suitable for release traceability.
- Do not declare R25 eliminated.
- Do not declare FR-07/08/09 fully release-verified when later required slices/evals still block their complete requirement.

## In scope

Acceptance harnesses, fake/live Telegram smoke as approved, process restart/outage testing, evidence collection, runbook clarification, focused corrective fixes discovered within S1 ownership.

## Out of scope

R17, ticket-close lifecycle, onboarding, state ownership hardening beyond minimal CAS, browser resolution, full LLM policy/eval, backup/restore.

## Task acceptance criteria

- S1.7-AC-01: all blocking S1 acceptance cases pass with retained artifacts.
- S1.7-AC-02: current architecture docs match verified implementation.
- S1.7-AC-03: traceability distinguishes S1-complete work from parent requirements still blocked elsewhere.
- S1.7-AC-04: Redis and PostgreSQL outage semantics match ADRs.
- S1.7-AC-05: residual R25 disclosure and evidence are explicit.
- S1.7-AC-06: no old direct/non-durable pilot path remains reachable.

## Required QA design

Build an integrated matrix mapping each acceptance case to environment, fault injection, expected DB rows/state, expected HTTP behavior, expected Telegram behavior, logs/metrics, and retained artifact.

## Expected test levels

Full backend gate, integration suite, process/restart harness, fake Telegram E2E, selected manual staging smoke, documentation consistency checks.

## Impact and compatibility expectations

Any defect discovered must be mapped back to S1.1-S1.6 ownership. Do not broaden S1.7 into unrelated product repair.

## Rollback/degraded behavior

Failure means no pilot launch. Preserve internal/staging operation only until blocking evidence is green.

## Documentation updates

Complete S1 evidence index, update slice progress and risk remediation accurately, retain residual risks, and leave later-slice blockers unchanged.
