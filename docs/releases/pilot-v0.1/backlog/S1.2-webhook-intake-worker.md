# S1.2 — Webhook Intake and Dedicated Inbox Worker


## Goal

Make client, manager, and platform-admin Telegram webhook requests thin durable intake boundaries and move business processing to a dedicated recoverable Telegram inbox worker.

## Required behavior

Webhook request:

1. verifies the surface secret;
2. performs minimal structural validation;
3. resolves stable bot/project/platform identity;
4. durably accepts through S1.1;
5. returns 2xx only after durable acceptance;
6. returns retriable non-2xx with no business side effects when PostgreSQL acceptance fails;
7. never runs full graph/LLM processing in the HTTP request.

Worker:

- claims accepted work;
- dispatches client/manager/platform processing;
- records attempts and lifecycle outcomes;
- recovers after crash and lease expiry;
- serializes attempts for one logical update;
- preserves effectively-once internal behavior through idempotency guards;
- does not fix R17 or S3 close semantics inside this package.

Additional S1.2 contract:

- PostgreSQL inbox lifecycle is the only correctness authority for deciding whether a logical Telegram update receives a worker processing attempt.
- Worker-owned processing must remove, disable, or explicitly bypass the legacy `client_bot._skip_duplicate_update` / Redis `processed_update:{update_id}` guard.
- Redis may be used only for optional acceleration, wakeup, or observability. A stale Redis duplicate key must not suppress accepted inbox work, retryable failure retries, or updates whose identity differs by project, surface, or numeric Telegram bot ID.
- Worker dispatch must bind credentials from the current secret-owning project/platform configuration repository or settings, compare the configured numeric Telegram bot ID to the inbox identity, and call handlers only on exact match.
- Bot tokens, token hashes, webhook secrets, and usernames must not be stored in inbox identity, inbox payload, lifecycle errors, logs, or evidence.
- Handler invocation must go through a typed worker adapter outcome: `completed`, `completed_noop`, `retryable_failure`, or `terminal_failure`.
- Worker policy settings must be explicit and validated: poll interval, empty-poll backoff, batch size, lease duration, renewal interval, handler timeout, max attempts, retry backoff/cap, and graceful shutdown deadline.

## In scope

Webhook services/routes, dispatcher boundary, worker startup/shutdown, claim/retry/recovery loop, payload decoding, handler invocation adapters, lifecycle/error mapping, integration tests.

## Out of scope

Thread lease, runtime state CAS, outbound intent implementation, manager tenant authorization, close idempotency, onboarding UX.

## Task acceptance criteria

- S1.2-AC-01: webhook 2xx occurs only after durable inbox acceptance.
- S1.2-AC-02: PostgreSQL failure returns retriable non-2xx and produces no handler side effect.
- S1.2-AC-03: duplicate accepted/completed update does not create parallel business processing.
- S1.2-AC-04: worker crash after claim is recoverable after lease expiry.
- S1.2-AC-05: retryable failure preserves attempt history and eventually retries under policy.
- S1.2-AC-06: terminal invalid update does not retry forever.
- S1.2-AC-07: Redis outage does not prevent durable intake or PostgreSQL-backed worker recovery.
- S1.2-AC-08: old direct synchronous paths are removed or proven unreachable for pilot webhook traffic.
- S1.2-AC-09: stale Redis duplicate keys cannot suppress accepted inbox work or retry attempts.
- S1.2-AC-10: worker dispatches using only currently bound credentials whose configured numeric bot ID matches the inbox identity.
- S1.2-AC-11: invalid intake inputs have deterministic HTTP outcomes and never create fallback identities.
- S1.2-AC-12: worker policy settings are explicit, validated, bounded, and prevent infinite retry.

## Required QA design

Cover three Telegram surfaces, duplicate delivery during every lifecycle state, DB outage before acceptance, process kill points, poison payload, shutdown/restart, polling/wakeup loss, retry exhaustion, and regression of existing webhook authenticity.

## Expected test levels

HTTP/webhook contract tests, worker/PostgreSQL integration, restart/lease-time tests, handler-dispatch characterization, security tests.

## Impact and compatibility expectations

Inspect every webhook route, dispatcher, handler signature, composition root, background worker process, health/readiness behavior, shutdown handling, and tests that assume synchronous response delivery.

## Observability requirements

Metrics/logs for accepted, duplicate, claimed, retryable, terminal, stuck, recovered, processing latency, and PostgreSQL intake failures.

## Rollback/degraded behavior

Do not acknowledge updates without durable acceptance. Before full package readiness keep pilot traffic disabled or operator-held; do not restore unsafe synchronous non-durable acknowledgement.
