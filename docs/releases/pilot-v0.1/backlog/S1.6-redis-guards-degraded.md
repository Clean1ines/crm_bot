# S1.6 — Redis Runtime Guards and Degraded Mode


## Goal

Wire production runtime-limit accounting while preserving PostgreSQL-owned intake and correctness during Redis outage.

## Required behavior

- Production composition supplies the real cache/accounting implementation.
- Healthy Redis enforces configured request/concurrency limits.
- Redis outage does not lose durable intake or weaken DB thread lease/CAS.
- Limit guarantee enters explicit degraded state with alert/metric.
- If limits are contractual, release compliance is degraded/blocked as documented.
- No silent `NullCache` behavior in production pilot composition.

## In scope

Cache factory wiring, guard accounting, failure/degraded policy, metrics/logs, composition and integration tests.

## Out of scope

Contractual SLA beyond NFR-05, business analytics S9, replacing PostgreSQL correctness with Redis, general autoscaling.

## Task acceptance criteria

- S1.6-AC-01: healthy accounting enforces configured limits.
- S1.6-AC-02: production composition does not use `NullCache` for pilot guards.
- S1.6-AC-03: Redis outage preserves durable acceptance and thread correctness.
- S1.6-AC-04: degraded limit state is operator-visible.
- S1.6-AC-05: recovery restores accounting without corrupting durable work.

## Required QA design

Cover Redis unavailable at startup and runtime, partial command failure, counter TTL/boundaries, multiple workers, recovery, burst traffic, and configuration edge cases.

## Expected test levels

Guard unit tests, Redis integration, composition tests, failure integration with PostgreSQL intake/lease/CAS active.

## Rollback/degraded behavior

Disable limit guarantee, reduce worker concurrency, keep PostgreSQL processing safety active. Do not stop durable intake merely because Redis is unavailable.

## Documentation updates

R24/NFR-05 only; do not attach R24 to S9 business metrics.
