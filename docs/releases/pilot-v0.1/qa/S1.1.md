## State And Invariant Model

### Proposed States

| State | Meaning | Terminal | Claimable |
|---|---|---:|---:|
| `received` | Durable intake accepted; no worker currently owns processing. | no | yes |
| `processing` | One worker owns a non-expired processing lease. | no | no while lease valid |
| `retryable_failed` | Attempt failed and can be retried when policy permits. | no | yes when retry due |
| `terminal_failed` | Update cannot or must not be retried. | yes | no |
| `completed` | Internal processing outcome completed. | yes | no |

### Required Fields

- Identity: `telegram_surface_or_role`, `project_id` when project-scoped, platform scope marker when platform-scoped, persisted numeric Telegram bot account ID from `getMe`, `telegram_update_id`.
- Payload: original update payload, ideally bounded/compressed only if approved; never secret identity material.
- Lifecycle: `status`, `received_at`, `started_at`, `completed_at`, `failed_at`, `updated_at`.
- Ownership: `owner_token`, `owned_by`, `lease_expires_at`.
- Attempts/errors: `attempt_count`, `last_error_kind`, bounded `last_error_message`, `next_attempt_at`.
- Duplicate diagnostics: `duplicate_count`, `last_duplicate_at`.
- Anomaly diagnostics: `payload_anomaly_count`, `last_payload_anomaly_at`, bounded anomaly metadata or hash.

### Invariants

- Unique identity is not secret-derived and not username-derived.
- `project_id + role + update_id` without persisted numeric bot ID is invalid.
- Internal generation identity is not an allowed S1.1 implementation choice.
- Legacy bot configuration rows may have nullable numeric bot ID, but S1.2 intake must not be enabled for those rows until controlled `getMe` backfill/onboarding fills it.
- `processing` requires `owner_token`, `owned_by`, and `lease_expires_at`.
- Non-processing states must not keep an active owner token.
- `attempt_count >= 0`.
- Duplicate intake may update only diagnostic duplicate fields.
- Duplicate intake never changes `status`, `owner_token`, `owned_by`, `lease_expires_at`, `attempt_count`, errors, completion/failure timestamps, original payload, or outbound state.
- Differing payload for same identity records anomaly and preserves original payload.
- Claim from `received` or due `retryable_failed` increments `attempt_count` exactly once for that claim.
- Reclaim after lease expiry is serial; stale owner cannot renew, complete, or fail.
- `completed` and `terminal_failed` are terminal for S1.1 repository lifecycle.

## Concurrency And Recovery Matrix

| Case | Required proof |
|---|---|
| Concurrent initial insert | Separate asyncpg connections/transactions race on the unique key; exactly one durable row results. |
| Concurrent duplicate during processing | Duplicate intake is a non-lifecycle mutation and cannot steal or renew owner. |
| Concurrent claim | Use row lock or atomic conditional update; one owner token wins; attempt count increments once. |
| Lease expiry and reclaim | Expired `processing` row can be reclaimed by a new owner in a serial attempt. |
| Stale owner after reclaim | Old owner cannot renew, complete, or fail the update. |
| Process crash after claim | S1.1 repository must expose enough lease metadata for S1.2 worker recovery after expiry, but S1.1 does not implement the worker. |
| Retry after failure | `retryable_failed` is claimable when due; attempt count increments on claim. |
| Terminal state preservation | `completed` and `terminal_failed` cannot be reopened by duplicate intake or stale owner. |

## Migration And Existing-Data Cases

- Clean database: migration creates table, constraints, indexes, comments if used, and no references to missing tables.
- Existing database: migration does not mutate existing `projects`, `clients`, `threads`, `messages`, or `events` data.
- Rerun: all `CREATE TABLE/INDEX/CONSTRAINT` behavior must be idempotent or covered by a forward-fix migration note.
- Partial crash: because `migrations/run_all.py` records the marker after executing SQL, tests must include a forward-fix/rerun scenario for table-created/index-missing and constraint-missing states.
- Uniqueness: deterministic unique constraint/index on `(surface_or_role, scope kind/project scope, persisted numeric Telegram bot ID, update_id)`.
- Bot identity source: S1.1 selects numeric Telegram bot ID from `getMe` and stores it in PostgreSQL with project/platform bot configuration. Tests must cover nullable legacy bot ID rows and replacement updates.
- Controlled activation: before S1.2 intake is enabled for a bot configuration, numeric bot ID must be filled by controlled `getMe` backfill/onboarding. S1.1 does not implement that backfill/onboarding step.
- Rollback/degraded: schema may remain unused until S1.2; rollback must not route live webhooks to an incomplete inbox.

## External Dependency And Ambiguity Cases

- S1.1 has no live Telegram network calls in repository primitives. It defines PostgreSQL persistence for numeric Telegram bot ID obtained by a controlled `getMe` onboarding/backfill step, but does not implement that step.
- S1.1 has no Telegram outbound delivery and must not claim to close R25.
- Redis is not a correctness dependency for S1.1.
- PostgreSQL unavailable means no durable acceptance can occur; HTTP behavior is owned by S1.2, but S1.1 repository must fail explicitly rather than falling back to volatile storage.
