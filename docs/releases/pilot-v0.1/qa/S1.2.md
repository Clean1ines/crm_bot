## PostgreSQL Authority Contract

- PostgreSQL inbox lifecycle is the sole correctness authority for deciding whether a durable logical update should receive a processing attempt.
- Worker-owned processing must not use `client_bot._skip_duplicate_update` or Redis key `processed_update:{update_id}` as a gate.
- The legacy Redis duplicate guard must be removed from the worker adapter, disabled for worker-dispatched client processing, or explicitly bypassed by a worker-only handler path. The implementation choice must be explicit in code and tests.
- A stale Redis duplicate key cannot suppress accepted inbox work.
- A first attempt that creates an old Redis key side effect and then fails retryably must still allow the next real inbox attempt to call the handler again.
- The same Telegram `update_id` in different projects, surfaces, or numeric Telegram bot IDs must not collide or suppress processing.
- Redis may be used only as optional wakeup, cache, acceleration, or observability. It must not be an intake, dedupe, retry, or ownership correctness boundary.

## Worker Credential Binding Contract

Worker dispatch must not store or recover credentials from inbox identity or payload. For each claimed row, the worker must:

1. read surface, project/platform scope, persisted numeric Telegram bot ID, and update ID from inbox identity;
2. resolve the current bot configuration from the secret-owning project/platform repository or settings;
3. obtain the current credential only from that repository/settings boundary;
4. compare the configured numeric Telegram bot ID to the inbox `telegram_bot_id`;
5. call the handler only on exact numeric bot ID match.

| Credential state | Required outcome |
|---|---|
| Current configuration numeric bot ID matches inbox identity | Processing is allowed with the current credential. |
| Current configuration numeric bot ID is temporarily `NULL` | Bounded `retryable_failed` configuration failure; no handler call. |
| Token rotated for the same Telegram account and successful `getMe` restored the same numeric bot ID | Processing is allowed with the new current credential. |
| Current configured bot ID differs from inbox bot ID | Do not use the new token for the old update; record controlled `terminal_failed` or dead-letter/operator-visible outcome. S1.2 chooses `terminal_failed` with bounded `credential_bot_mismatch`. |
| Project/platform configuration is absent or disabled before processing | Record controlled `terminal_failed` with bounded `configuration_missing` or `configuration_disabled`; no handler call. |
| Platform credential mismatch | Record controlled `terminal_failed` with bounded `credential_bot_mismatch`; no handler call. |

Token, token hash, username, and webhook secret must never appear in inbox identity, original payload enrichment, lifecycle errors, logs, or evidence. S1.2 must not implement historical credential storage without a separate ADR; mismatch blocks dispatch.

## Worker Policy And Configuration Invariants

S1.2 implementation must introduce explicit validated settings or equivalent injected policy for:

- poll interval;
- empty-poll backoff;
- batch size;
- lease duration;
- renewal interval;
- handler timeout;
- max attempts;
- retry backoff and cap;
- graceful shutdown deadline.

Required invariants:

- `batch_size > 0`;
- `lease_duration > 0`;
- `0 < renewal_interval < lease_duration`;
- `handler_timeout > 0`;
- `max_attempts > 0`;
- polling and empty-poll backoff are bounded;
- retry cannot be infinite;
- worker does not claim new rows after shutdown begins;
- graceful shutdown leaves unfinished work reclaimable;
- lost lease or owner means the worker must not complete, retry-fail, or terminal-fail the row as a stale owner.

Failure classification:

- handler timeout or transient infrastructure failure -> `retryable_failed`;
- malformed persisted payload or permanent route/credential mismatch -> `terminal_failed`;
- retries exhausted -> `terminal_failed` with bounded `max_attempts_exhausted`;
- lost renewal/ownership during long handler -> no complete/fail mutation by stale owner, row remains recoverable by lease expiry or already owned by another worker.

## Worker Processing Adapter Contract

Worker handler adapters must return a structured outcome:

- `completed`;
- `completed_noop`;
- `retryable_failure`;
- `terminal_failure`.

The worker must not treat arbitrary `None` from a legacy handler as success without adapter semantics. The adapter must:

- call client/manager/platform processing only from the worker;
- convert known exceptions and timeouts into lifecycle outcomes;
- preserve cancellation semantics;
- not complete or fail a row after ownership is lost;
- not call a handler more than once inside one claim attempt;
- let handler spies prove both request-path absence and worker-path invocation.

Impact surface for existing callers:

- `src/interfaces/http/webhooks.py` route dependencies for client, manager, platform, legacy client, and legacy manager paths;
- `src/application/services/webhook_dispatcher.py`;
- `src/interfaces/telegram/client_bot.py:process_client_update`;
- `src/interfaces/telegram/manager_bot.py:process_manager_update`;
- `src/interfaces/telegram/platform_bot.py:process_admin_update`;
- `tests/api/test_webhooks.py` synchronous-dispatch expectations.

## Concurrency And Recovery Matrix

| Case | Required proof |
|---|---|
| Concurrent webhook duplicates | Separate requests for same identity produce one durable logical row; both safe responses; no handler call in HTTP path. |
| Cross-scope same update ID | Separate projects, surfaces, or numeric bot IDs with the same `update_id` are independently accepted and processed. |
| Concurrent workers claim | Multiple workers/pools call claim; one active owner per update. Use S1.1 `claim_next`/`claim_by_id`, not custom SQL. |
| Bounded batch size | Worker processes no more than configured batch size and yields between polls. |
| Lease renewal | Long handler path renews before expiry; if renewal fails, stale owner cannot complete/fail. |
| Crash after claim | Kill/cancel worker after claim; after lease expiry a fresh worker discovers via `reclaim_expired_batch` and retries serially. |
| Expired lease discovery after restart | New worker with no known inbox IDs finds stale processing rows and invalidates old owner. |
| Retryable failure | Handler exception/timeout or temporary NULL bot ID records bounded retryable failure and next retry policy. |
| Terminal failure | Malformed persisted payload, permanent route mismatch, credential mismatch, deleted config, or retry exhaustion becomes terminal. |
| Stale owner rejection | Old owner cannot complete/fail after lease expiry and reclaim. |
| Graceful shutdown | Shutdown event stops new claims; unfinished work completes within deadline or remains reclaimable. |
| PostgreSQL unavailable during worker loop | Worker logs/backs off without losing already accepted rows. |
| Redis unavailable during worker loop | Worker correctness remains PostgreSQL-backed; degraded state is visible. |
